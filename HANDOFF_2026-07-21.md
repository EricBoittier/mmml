# Hand-off — mmml SpookyPhysNet / PBC dynamics investigation (2026-07-21)

## Bugs found and FIXED today (all synced to pc-studix, none committed to git)

1. **Flat orbax checkpoint-format detection**
   `mmml/utils/model_checkpoint.py`, `mmml/models/physnetjax/physnetjax/restart/restart.py:get_last`.
   New training runs save a flat `manifest.ocdbt` checkpoint (no `epoch-*/` wrapper); loaders only
   recognized the old nested layout. Fixed detection + switched to the device-agnostic
   `_restore_pytree_cpu_safe` restore path.

2. **Architecture mis-selection (the big one)**
   `mmml/utils/model_checkpoint.py:build_physnet_from_config`. Checkpoints with
   `model_attributes["model_type"] == "spooky"` were being silently loaded as plain `PhysNet`
   instead of `SpookyPhysNet`. Now checks `model_type` and picks the right class. Confirmed via
   `class: SpookyPhysNet` in FD-check output and energy going from a nonsensical value to a sane one.

3. **`jax_pme` ewald-method crash**
   `mmml/interfaces/pycharmmInterface/mm_energy_forces.py:_wrap_mm_fn_with_jax_pme_coulomb`.
   The wrapped `mm_fn` was missing a `charges` kwarg that every other `mm_fn` variant in the module
   accepts. Fixed — `--lr-solver jax_pme --jax-pme-method ewald` no longer crashes with
   `TypeError: ...wrapped() got an unexpected keyword argument 'charges'`.

4. **Sparse active-dimer cap silently undersized for dense liquids (root cause of NVE
   instability/velocity spikes)**
   `mmml/interfaces/pycharmmInterface/mlpot/mlpot_sparse_dimer_policy.py:resolve_max_active_dimers`
   + call site in `mmml/interfaces/pycharmmInterface/mmml_calculator.py` (~line 1156-1186).
   Old formula: `cap = max(4005, 6 * n_monomers)` — assumes ~6 neighbors/monomer, fine for sparse
   clusters, badly wrong for dense periodic liquids (TIP3:903 @ ~1g/cm³ has ~57 neighbors/monomer
   within the 7.5 Å active radius — cap was `5418` vs. `~26,480` true in-range pairs, only ~21%
   coverage). `jnp.nonzero(mask, size=cap)` then silently truncates to "first N pairs by
   canonical enumeration order", not nearest — proven via a direct perturbation test (nudging one
   monomer flips an unrelated, uninvolved pair's interaction on/off with no other change).
   **Fix**: cap is now density-aware when box volume is known — computed from
   `n_monomers * (4/3 π active_radius³ / box_volume) / 2 * SPARSE_DIMER_CAP_SAFETY_MARGIN`.
   Margin currently `1.1` (user request, down from an initial `1.5` which produced a cap so large
   the compile time became impractical — see below). Falls back to the old heuristic when no
   box_volume/active_radius is available (unchanged behavior for existing non-PBC callers).
   **Also added**: a `jax.lax.cond` + `jax.debug.print` runtime warning inside the JIT'd
   sparse-selection code (`mmml_calculator.py` ~line 2117-2137) that fires whenever the true
   in-range count exceeds the cap, so any future saturation is loud, not silent (per the project's
   documented "never silently skip failures" rule). **This warning is confirmed working** — it
   fired correctly (with correct diagnostic numbers) on an independent TIP3:548 run the user had
   going separately.
